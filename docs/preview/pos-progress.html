Bugs the testing caught

Three defects that would have reached customers. Each surfaced only because the code was run against a real PostgreSQL rather than the convenient one.

Tenant isolation was switched off

The command used to scope each request to one customer silently does not accept parameters in PostgreSQL. Every tenant-scoped request would have failed in production, and the isolation it was meant to enforce was never actually active. In a product sold to many restaurants, that is one customer seeing another's sales.

The database and the code disagreed

Columns existed in one definition and not the other — a field stored as structured data in the database but plain text in the code, a staff PIN the database required that the migration deliberately leaves empty. A test now compares the two on every run, so they cannot drift apart quietly again.

A password shipped in the source

Deploying without setting a signing key fell back to a default written into the code itself. Anyone with a copy could have issued themselves a valid tablet login for any customer. The server now refuses to start rather than run in that state.

Decisions worth knowing

Four choices that shape everything built on top.

Money is never a decimal

All amounts are whole halalas. Fractional arithmetic drifts, and a bill off by one halala is a wrong tax invoice. VAT is derived by subtraction so net, tax and total always reconcile — tested against every price from 0.01 to 50.00 SAR.

Every tablet stamps its own receipts

Each device registers with ZATCA in its own right. If one tablet dies, the rest keep selling and keep printing legal receipts. Nothing in the billing path needs the network, or the other tablets.

Sales can be added, never removed

The application has no permission to delete a sale — the database refuses it outright. Corrections are credit notes. A tax record that can be deleted is not a tax record.

Old staff PINs were left behind

PixelPoint contained one login code: the vendor default, 12345. Carrying that forward would ship an open door to every customer. All 13 staff start with no PIN and must set one.

What is not done

The honest list, worst first.

Blocking

ZATCA has never seen these invoices. The library is provably self-consistent, which is not the same as compliant. Canonicalisation, hash encoding and rounding all need checking against ZATCA's own validator, and the signature block inside the invoice is still an empty placeholder. Sandbox credentials from the ZATCA portal are needed to go further.

Not started

The till application. Menu grid, order taking, payment, receipt printing, offline queue, and the hub role that lets waiters share tables. The largest remaining body of work, and the only part a customer will ever see.

Not started

Sending sales onward. Finished sales are stored and marked pending; nothing yet forwards them to the ERP or reports them to ZATCA. The ERP side is waiting on answers about its integration contract.

Risk

The schema is defined twice. Once in code, once in SQL, both maintained by hand. They have already drifted apart once. A test now catches it, but proper migrations would remove the problem rather than police it.
